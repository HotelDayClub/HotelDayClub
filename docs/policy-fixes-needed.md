# Policy fixes still needed

The privacy policy at `/privacy` (`legal/privacy-policy.md`) was not changed. This note is for Jason and a lawyer. It walks every mismatch listed in `docs/data-inventory.md` and says whether the code now matches that sentence or the wording should change.

Nothing here is proposed legal text to publish. It is a factual reading of the code after the hotel-password, admin-login and booking-page changes.

## Code now matches, or is closer

### 4. Booking link

The inventory said anyone with `/booking/<code>` could see the guest's full name and the full email.

The page now shows a first name and last initial (for example `Persis G.`), and an email like `p***@example.com`. It does not show the full name, the full email, or the mobile number. It still shows the booking code, hotel, date, pass, party size, status, add-ons, the cancellation sentence, a QR code of the booking code, an "Add to calendar" file, and a directions link when the hotel has an address. The page is `noindex`, `robots.txt` disallows `/booking/`, and each address is limited to 30 lookups in 15 minutes. New booking codes are `HDC-` plus 32 random hex characters. Older short codes still open.

Suggested wording, if you want the policy to describe this page: "Your confirmation page shows the hotel, date, pass and booking code. Your name is shortened and your email is masked. Anyone with the link can see that page. The mobile number is not on it."

### 7. Security claims, in part

The policy says: "We use reasonable steps to protect personal information: access controls, strong passwords and two-factor authentication on admin accounts, encrypted connections, and giving hotels only the minimum details."

What the code does now:

- Hotel passwords are scrypt hashes with a random salt per password. A plaintext value already in the database is hashed on startup. The hash is not shown on a page, in the hotels CSV, or in the log.
- Hotel login uses a constant-time compare.
- Admin is still one shared `ADMIN_PASSWORD`. The compare is constant-time. After 5 failures from the same address, further tries wait 15 minutes.
- The admin cookie is HttpOnly, SameSite=Lax, expires after 12 hours, and is marked Secure when `NODE_ENV` is `production`. Hotel cookies use the same flags.
- There is no two-factor step. That was left out on purpose.

Suggested wording until two-factor exists: drop "two-factor authentication on admin accounts", or say it is not in place yet. Keep "encrypted connections" only if the live site is served over HTTPS (Render does that). "Giving hotels only the minimum details" is still too strong: see item 3.

`COOKIE_SECRET` is generated by Render. In production, a missing value or the built-in demo value is refused: the process logs an error and signs cookies with a random secret held only in memory, so sessions reset on restart. Outside production, an unset value still uses the demo default. That is not a policy sentence, but the "access controls" line assumes a stable secret.

## Policy wording needs to change

### 1. Payment provider (later feature)

The policy says: "Payment details: handled by our payment provider Stripe. We see only limited details (for example, card type, last 4 digits, and payment status). We don't store full card numbers."

The app still has no Stripe client and stores no card data. Checkout is a disabled demo form.

Suggested wording while this is a demo: "We do not take payment on this site yet. No card number is collected or stored. When payments start, a payment provider will handle the card, and we will describe here what limited details we see."

### 2. IP address on acceptance

The policy says acceptance records include "when you accepted our Terms, the hotel's rules and the risk warning, which version you saw, and the IP address used."

The booking still stores the three timestamps and the full rules and risk text. It does not store an IP address or a separate version number.

Suggested wording: "We store the time you accepted the terms, the hotel's rules and the risk warning, and the text you were shown."

### 3. What the hotel sees

Section 5 says the hotel receives "your name, booking code, pass and party size (and any notes you add)".

A logged-in hotel still sees the guest's email and mobile on its own dashboard, for its own bookings only. A test checks that a hotel cannot look up another hotel's guest. Checkout still says the name, email and mobile are shown to the hotel. The print list and the night-before preview still omit email and mobile.

Suggested wording: "The hotel you booked sees your name, email, mobile number, booking code, pass, party size and any note it records about your visit, so it can check you in. It does not see other hotels' guests."

### 5. No-show notes

The policy mentions "an incident or refused entry". The app also stores `guest_notes.kind = no_show` with the same free-text note (up to 200 characters). There is still no separate refused-entry flag, and no way in the product to delete a note.

Suggested wording: "The hotel can record a no-show or an incident against your booking, with a short note. That note can include what happened, which may be health information. We keep it with the booking."

### 6. Marketing opt-in and unsubscribe (later feature)

The policy says: "We send marketing emails or SMS (for example, hot-day alerts, new hotels and offers) only if you've opted in. Every marketing message identifies us and has an unsubscribe option, and we act on unsubscribes within 5 working days."

The app still only stores `marketing_opt_in` as 0 or 1. It does not send marketing email or SMS. It does send transactional email through Resend (HTTPS, not SMTP) when `RESEND_API_KEY` and `MAIL_FROM` are set: a booking confirmation to the guest, and an alert to the contact address for each contact-form message. If the key is unset, those sends are skipped and logged, and the booking or message is still saved. The messages are not marketing and have no unsubscribe link. There is no unsubscribe route and no record of an unsubscribe. The confirmation page says a confirmation email is sent to the address given. While the demo banner is on, the page and the guest email say no payment was taken and no real booking exists. The waitlist form tells people to email the contact address.

Suggested wording: "After you book, we email you a confirmation of that booking. If you use the contact form, we email that message to ourselves so we can reply. These are not marketing messages, so they do not include an unsubscribe link. You can tick a box to say we may email you about day passes. We do not send marketing email or SMS yet. To withdraw that choice, or to leave the waitlist, email us at the address in this policy. We do not have an unsubscribe link in the product yet."

### 8. Retention and deletion (later feature)

The policy says: "We keep booking and payment records for as long as needed for tax and legal purposes. We delete or de-identify guest lists and marketing data when no longer needed. Hotels are asked to delete guest lists after the visit."

There are still no payment records, no retention period, and no job that deletes or de-identifies bookings, guest notes, or the marketing flag. An admin can delete a waitlist row. Bookings cannot be deleted from the product. The newest 14 database backups can still contain a row after it is removed from the live file. Nothing in the product asks a hotel to delete a guest list.

Suggested wording: "We keep booking details, guest notes and the marketing choice until we delete them. There is no automatic deletion period. You can ask us to delete what we do not need to keep by emailing the address in this policy. A backup file may still hold a copy until that file is replaced. We do not yet ask hotels to delete their copy of a guest list after the visit."

### 9. Communications

The policy lists "Communications: emails, messages and complaints you send us."

The contact form at `/contact` stores the name, email, optional booking code, topic and message in `contact_messages`. When `RESEND_API_KEY` and `MAIL_FROM` are set, a copy is sent to the contact address through Resend. Inbound email to the mailbox is still not stored in the database. The `mailto:` link is still on the site.

Suggested wording: "If you send us a message through the contact form, we store your name, email, topic, message and any booking code, and we email a copy to our contact address so we can reply. If you email us directly, we keep that email in our mail, not in the booking database."

### 10. Server logs and backups

The policy does not mention logs or backups.

These are still true:

- If `WAITLIST_WEBHOOK_URL` is unset, each waitlist signup is written to the server log with email, first name, place, role, hotel name and destination. Webhook errors log the same fields.
- If `ADMIN_PASSWORD` is unset, the generated admin password is written once to the log. The generated demo hotel password is not written to the log.
- Admin can download a full SQLite backup and CSV files of bookings, hotels (no password column) and the waitlist. Fourteen backup files are kept when `DATA_DIR` is set.

Suggested wording: "We keep server logs that can include a waitlist signup if saving or forwarding it fails, or if the spreadsheet connection is off. We keep backup copies of the database for the operator. Those copies include booking and waitlist details. They are not public."

## Already matched, still worth leaving as written

### 11. Waitlist connection

The policy's description of the fields, the database, the optional copy to another store, and the lead event without personal details still matches the code. The log line in item 10 is the part the policy does not mention.

The Google Analytics sentences in section 2 still match the snippet: public guest pages only, no name, email, phone or booking code in the hit, and the lead event has no personal details.
